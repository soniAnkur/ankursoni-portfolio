MCP Apps

Putting a radio inside a chat

An assistant can tell you that Raga Multani belongs to the late afternoon. It cannot give you a seek bar. MCP Apps closes that gap by letting a server ship real UI to the client — here is how I wired my raga radio into one.

Ankur Soni·7 November 2026·9 min read

The gap text can't cross

Raga Radio generates instrumental Indian classical tracks. Each of its 68 ragas carries structured metadata — a thaat, an ascent and descent, a time window like Early Morning (4 AM – 7 AM), and a mood array such as ['Devotional', 'Peaceful', 'Romantic']. So "something devotional for a 5am sit" is a query a model handles well: it can name Ahir Bhairav and explain why it suits the hour. Then it stops. Audio needs a transport — play, pause, scrub, what's next — and a transport is a piece of interface, not a sentence.

MCP Apps is the part of the Model Context Protocol that lets a server return interface instead of prose. The server registers an HTML resource under a ui:// URI, binds it to a tool, and the host renders it in a sandboxed iframe that can call back into that same server.

MCP Apps is SEP-1865, an extension identified as io.modelcontextprotocol/ui, stable since 26 January 2026. No browser flag, no origin trial. It grew out of MCP-UI, and the spec credits Postman, Hugging Face, Shopify, Goose and ElevenLabs as the adopters whose implementations fed into it. Much of what is written about it predates that stable revision, which matters more than usual here: several field names changed on the way.

Three parties, two boundaries

The host owns the conversation. Your MCP server owns the tools and the UI resource. The iframe is the third thing: it runs your HTML, but on an origin the host controls, and it reaches your server only through the host.

Declaring the resource and the tool

Two registrations. The resource is the HTML; the tool is what the model can decide to invoke. The link between them is a single field: _meta.ui.resourceUri.

server.ts

import { z } from "zod";
import {
  registerAppTool,
  registerAppResource,
  RESOURCE_MIME_TYPE,
} from "@modelcontextprotocol/ext-apps/server";

// The UI itself. RESOURCE_MIME_TYPE is "text/html;profile=mcp-app" —
// a bare "text/html" will not be treated as an app resource.
//
// CSP lives on the RESOURCE, not the tool. Hosts read it from the
// resources/read content item; putting it on the tool is ignored.
registerAppResource(
  server,
  "Raga Radio Player",
  "ui://raga-radio/player",
  {
    _meta: {
      ui: {
        csp: {
          connectDomains: ["https://api.ragaradio.app"],
          resourceDomains: ["https://audio.ragaradio.app"],
        },
      },
    },
  },
  async () => ({
    contents: [{
      uri: "ui://raga-radio/player",
      mimeType: RESOURCE_MIME_TYPE,
      text: await readFile("dist/player.html", "utf8"),
    }],
  })
);

registerAppTool(
  server,
  "play_raga",
  {
    description: "Play a raga in the Raga Radio player.",
    // ZodRawShape, not raw JSON Schema — the SDK derives the schema.
    inputSchema: {
      raga: z.string().optional().describe("Raga id, e.g. ahirBhairav"),
      mood: z.string().optional().describe("Devotional | Peaceful | Romantic"),
    },
    _meta: { ui: { resourceUri: "ui://raga-radio/player" } },
  },
  // resolveTrack hits /api/tracks and filters on the raga's mood array —
  // the same endpoint and the same filter the web player already uses.
  async ({ raga, mood }) => {
    const track = await resolveTrack({ raga, mood });
    return {
      content: [{ type: "text", text: `Playing ${track.ragaName} — ${track.title}` }],
      structuredContent: track,
    };
  }
);

Two spellings exist; write the nested one. You will find material using the flat _meta["ui/resourceUri"]. It is deprecated and slated for removal before GA, but it still works today — hosts must check both, and registerAppTool quietly writes both keys for older clients. Write _meta.ui.resourceUri and let the SDK handle back-compat.

The CSP default that silently kills audio

This is the part that cost me an evening, and it is specific to anything media-shaped. If you omit _meta.ui.csp, the host applies a deliberately brutal default: 

default-src 'none';
script-src 'self' 'unsafe-inline';
style-src 'self' 'unsafe-inline';
img-src 'self' data:;
media-src 'self' data:;
connect-src 'none';

Two directives in there will ruin your evening. connect-src 'none' kills every fetch, so the track list never arrives. media-src 'self' data: allows audio only from the sandbox's own origin, so even a URL you hardcode will not play. The player renders. The controls respond. The audio element gets a URL and fetches precisely nothing, usually without a useful error.

A radio streaming from Cloudflare R2 therefore has to declare both up front — connectDomains for the API it reads track lists from, resourceDomains for wherever the audio actually lives.

The debugging note that cost me the time: the violation fires inside the sandbox, on an origin you do not own, so it never reaches your server logs. Open the host's console, not yours.

The handshake

Older MCP-UI material describes an ui-lifecycle-iframe-ready message. That is pre-SEP. The stable spec replaced it with proper JSON-RPC 2.0 over postMessage, and ui/initialize is the entry point.

Inside the iframe

The player is an ordinary web page with one extra thing: an App instance that receives tool input and can call tools itself. The DOM-style setters are the whole API surface you need — ontoolinput fires when the model invokes play_raga, and callServerTool goes the other way when the user presses skip.

player.ts — runs inside the sandbox

// App is exported from the package root. The /app-bridge subpath is the
// host side of the connection — AppBridge, PostMessageTransport — not this.
import { App } from "@modelcontextprotocol/ext-apps";

const app = new App({ name: "RagaRadio", version: "1.0.0" }, {});

// The model called play_raga. Arguments arrive before the result does,
// so the UI can show the raga name while the track is still resolving.
app.ontoolinput = ({ arguments: args }) => {
  ui.showPending(args.raga ?? args.mood);
};

app.ontoolresult = ({ structuredContent: track }) => {
  audio.src = track.audioUrl;
  ui.render({
    title: track.ragaName,
    thaat: track.thaat,
    time: track.time,
    moods: track.mood,
  });
  audio.play();
};

await app.connect();

// User pressed skip inside the iframe. This is a tool call that the model
// never initiated — the host still brokers and can still refuse it.
skipButton.addEventListener("click", async () => {
  const next = await app.callServerTool({
    name: "next_track",
    arguments: { after: currentTrackId },
  });
  ui.render(next.structuredContent);
});

Hiding the transport from the model

next_track and set_volume are things the player needs. The model has no business deciding to change your volume, and every tool you expose costs context and invites misuse. The visibility field solves this cleanly: 

_meta: {
  ui: {
    resourceUri: "ui://raga-radio/player",
    // Default is ["model", "app"]. Dropping "model" means the agent
    // cannot see or call this tool — only the iframe can.
    visibility: ["app"],
  },
}

So play_raga stays conversational and next_track becomes a button that happens to be implemented as a tool.

Degrade when there is no UI

Not every host renders apps. The spec is explicit that servers should check before assuming, and register a text-only variant when the capability is absent: 

import { getUiCapability, RESOURCE_MIME_TYPE } from "@modelcontextprotocol/ext-apps/server";

// getUiCapability takes the CLIENT's capabilities, which only exist once
// the connection is initialized — so this cannot run at module load.
server.server.oninitialized = () => {
  const ui = getUiCapability(server.server.getClientCapabilities());

  if (ui?.mimeTypes?.includes(RESOURCE_MIME_TYPE)) {
    registerAppResource(server, "Raga Radio Player", "ui://raga-radio/player", cspMeta, read);
    registerAppTool(server, "play_raga", withUi, handler);
  } else {
    // Same tool, same arguments, prose instead of a player.
    server.registerTool("play_raga", textOnly, async (args) => ({
      content: [{ type: "text", text: describeTrack(await resolveTrack(args)) }],
    }));
  }
};

What it looks like when it runs

You type "something devotional for a 5am sit". The model has the raga metadata in the tool schema, so it picks play_raga with { mood: "Devotional" } and leaves raga empty — it does not need to know the catalogue, only that mood is a legal filter.

The host opens the sandbox and loads ui://raga-radio/player. Before the track resolves, ontoolinput has already fired, so the player paints "Devotional" and a spinner rather than an empty box. resolveTrack filters the 68 ragas on the mood array, prefers the ones whose time window covers 5am, and returns Ahir Bhairav. ontoolresult sets audio.src and playback starts.

Total visible latency is the track lookup, because the UI was on screen before the answer existed. That ordering — input notification first, result second — is the detail that makes these feel like applications rather than slow tool calls.

What this doesn't solve

Everything above puts a player inside the chat. The server owns the UI, the host renders it, the lifetime is the tool call. That is the right shape when the assistant is the surface you are working in.

It is the wrong shape for a different and equally real case: the radio is already open in a browser tab, playing, signed in — and you want to say "skip this, put on something peaceful" without moving to a chat window at all. No ui:// resource helps there, because the UI is not the thing that is missing. What is missing is a way for an agent to reach into a page that already exists.

That is a different specification, at a very different level of maturity.
