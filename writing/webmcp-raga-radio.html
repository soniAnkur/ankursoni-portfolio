Web MCP

Driving a tab you already have open

The radio is playing. You are signed in. You want to say "put on something peaceful" without opening a chat window. WebMCP lets the page itself hand its controls to an agent — and it is a far rawer proposition than MCP Apps.

Ankur Soni·7 November 2026·8 min read

A different missing piece

In the previous post the problem was that a chat client had no player, so the server shipped one. Here the problem is inverted. The player exists. It is open, it has state, it has my session. The thing that cannot reach it is the agent.

Conventional automation answers this by pretending to be a user: drive the DOM, click the buttons, hope the markup did not change. That works until a class name changes, and it never knows what any control means. WebMCP proposes the opposite — the page declares what it can do, in the same vocabulary MCP already uses, and the agent calls those declarations directly.

Status, plainly. WebMCP is a Draft Community Group Report from the W3C Web Machine Learning CG, dated 2 November 2026. It is not a W3C Recommendation. Chrome has shipped it behind an origin trial since Chrome 149, with a local flag at chrome://flags/#enable-webmcp-testing. Build on it to learn; do not build a product that depends on it.

It moved, and most write-ups are stale

If you read one thing before writing code: the API lives on document, not navigator. The CG moved the getter because tools belong to a document rather than the browser as a whole — a reasonable call, since two tabs of the same app should expose their own state. Chrome 150 deprecated navigator.modelContext while the trial ships both.

There is also no provideContext(), despite it appearing in a good deal of otherwise-sensible material. The current interface is three methods:

WebIDL — abridged

partial interface Document {
  [SecureContext, SameObject] readonly attribute ModelContext modelContext;
};

interface ModelContext : EventTarget {
  Promise<undefined> registerTool(ModelContextTool tool, optional ModelContextRegisterToolOptions options = {});
  Promise<sequence<RegisteredTool>> getTools(optional ModelContextGetToolOptions options = {});
  Promise<DOMString> executeTool(RegisteredTool tool, optional object inputObject, optional ModelContextExecuteToolOptions options = {});

  attribute EventHandler ontoolchange;
  attribute EventHandler ontoolactivated;
  attribute EventHandler ontoolcancel;
};

The shape of it

There is no server and no iframe. The page, the tools and the state are one thing, inside one origin, under the user's existing session.

Registering the tools

Raga Radio's data makes the tool definitions almost write themselves. Every raga already carries a mood array and a time window, so "peaceful" and "something for this hour" are lookups, not guesses.

Three things below come from the app, not from WebMCP: ALL_RAGAS is the catalogue exported by src/data/ragas.js, player is the audio controller the on-screen buttons already call, and resolveRaga matches an id or display name against that catalogue. The tools are a second doorway into code that already runs.

player-tools.js

// Chrome 150 deprecated the navigator form; keep the fallback while the
// origin trial ships both, and drop it once the trial ends.
const mc = document.modelContext ?? navigator.modelContext;

const controller = new AbortController();

// ragas.js exports an object keyed by id, so flatten it once and keep
// the id alongside the record.
const ALL_RAGAS = Object.entries(ragas).map(([id, r]) => ({ id, ...r }));

await mc?.registerTool({
  name: "play_raga",
  title: "Play a raga",
  description:
    "Play a specific raga in the radio. Accepts a raga id such as " +
    "'ahirBhairav' or a display name such as 'Ahir Bhairav'.",
  inputSchema: {
    type: "object",
    properties: {
      raga: { type: "string", description: "Raga id or display name" },
    },
    required: ["raga"],
  },
  annotations: { readOnlyHint: false },
  async execute({ raga }) {
    const match = resolveRaga(raga);
    if (!match) return { ok: false, reason: `Unknown raga: ${raga}` };

    await player.play(match.id);
    return {
      ok: true,
      nowPlaying: match.name,
      thaat: match.thaat,
      time: match.time,
      mood: match.mood,
    };
  },
}, { signal: controller.signal });

The second tool is the one that makes this feel like a radio rather than a jukebox. It takes a mood, filters the catalogue, and starts playing — the user never names a raga at all. 

await mc?.registerTool({
  name: "set_mood",
  title: "Set the mood",
  description:
    "Filter the station by mood and start playing. Moods include " +
    "Devotional, Peaceful, Romantic, Serious, Majestic.",
  inputSchema: {
    type: "object",
    properties: {
      mood: { type: "string" },
      respectTimeOfDay: {
        type: "boolean",
        description: "Prefer ragas whose traditional time window matches now",
      },
    },
    required: ["mood"],
  },
  annotations: { readOnlyHint: false },
  async execute({ mood, respectTimeOfDay = true }) {
    // Each raga carries mood: ['Devotional', 'Peaceful', 'Romantic']
    let pool = ALL_RAGAS.filter((r) =>
      r.mood.some((m) => m.toLowerCase() === mood.toLowerCase())
    );

    if (respectTimeOfDay) {
      const byHour = pool.filter((r) => windowCovers(r.time, new Date()));
      if (byHour.length) pool = byHour;
    }

    if (!pool.length) return { ok: false, reason: `No ragas match ${mood}` };

    const chosen = pool[Math.floor(Math.random() * pool.length)];
    await player.play(chosen.id);
    return { ok: true, nowPlaying: chosen.name, matched: pool.length };
  },
}, { signal: controller.signal });

// Unregistering is the signal, not a method.
window.addEventListener("pagehide", () => controller.abort());

The lifecycle

Registration happens on load; discovery happens whenever the agent looks; execution runs your callback in the page. The tools live exactly as long as the tab does.

Three things that bite

Results are strings

executeTool resolves to a DOMString. Your callback can return an object, but it is serialized to JSON on the way out — and anything non-serializable raises unserializable result as an OperationError. If you are coming from MCP server work, resist the urge to return { content: [{ type: "text", … }] }. That shape belongs to the other protocol.

Permissions Policy, not a prompt

The feature is gated by a Permissions Policy feature named "tools", whose default allowlist is ['self']. Same-origin works out of the box; a cross-origin iframe that wants to register tools must be granted it explicitly, and calling without permission throws NotAllowedError. It is also [SecureContext] — HTTPS or localhost only.

Note what is not there: no user-gesture requirement in the spec. A page can register tools on load. The protection is that the user chose to open the page, which is a weaker guarantee than the MCP Apps sandbox gives you and deserves thought before exposing anything destructive. That is what annotations.consequentialHint is for.

Descriptions are the API

The model picks a tool by reading its description. "Set the mood" is a worse description than naming the actual moods, because the latter tells the model what values are legal. This is prompt engineering wearing an IDL costume, and it is where most of the quality lives.

Against MCP Apps

The two specifications are not layered. Nothing in either references the other. What they share is MCP's tool vocabulary — a name, a description, a JSON Schema — which is why play_raga can be described almost identically in both while executing completely differently.

Direction
MCP Apps: server hands UI to the client. WebMCP: page hands tools to an agent.
What's missing
MCP Apps supplies interface the chat lacks. WebMCP supplies reach into interface that already exists.
Trust boundary
Sandboxed remote HTML on a host-controlled origin, versus a first-party page the user opened.
Lifetime
A tool call, versus as long as the tab is alive.
Session and auth
Server must handle its own. WebMCP inherits whatever the user is already signed into.
Maturity
Stable since January 2026, versus a Draft CG Report behind an origin trial.

Where I landed

For Raga Radio they answer different questions, and I would ship them for different reasons. The MCP App is the one I would actually put in front of people now: stable, host support that exists, and it solves a real problem — an assistant that can reason about ragas but cannot play one.

WebMCP is the more interesting idea and the less finished one. A page that publishes its own capabilities, in a vocabulary agents already speak, with the user's session intact, is a better long-term answer than any amount of DOM-scraping automation. It has also already moved once from navigator to document, which tells you roughly how settled it is.
